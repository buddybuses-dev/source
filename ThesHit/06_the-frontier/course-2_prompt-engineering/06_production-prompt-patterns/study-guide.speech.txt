What This Module Covers

A prompt that works once in a chat window is a demo. A prompt that works ten thousand times a day inside a system you shipped is infrastructure. Module 6 is where you make that jump: everything you built in M1 through M5 now gets packaged into patterns that survive contact with production traffic.

You will learn to treat prompts as versioned, reusable assets: templates with variable injection instead of hand-edited strings, guardrails and validation instead of hoping the model behaves, and retry and fallback logic for when it does not. You will also build prompt libraries for reuse across projects, plus a cost model and caching strategies for production economics. This is the mindset M7, the capstone, assumes you already have.

Why It Matters

Picture a customer support bot handling 10K conversations a day. A prompt that fails on 2 percent of inputs means 200 broken customer interactions daily. A hobbyist tweaks the prompt and hopes. A professional wraps it in validation, catches malformed output before the customer sees it, retries with a corrective message, and falls back to a safe degraded response. The difference is not wording. It is architecture.

The economics matter just as much. At production volume, every token is a recurring cost. A 3,000 token system prompt running 50K calls a day is a real line item, and a cached prefix versus an uncached one can change that line by an order of magnitude. Builders in The Faction who master these patterns ship systems that are cheaper to run, harder to break, and faster to extend. Builders who skip them ship systems that quietly bleed money and trust.

What You Need to Know

Prompts as Infrastructure

A production prompt is a versioned artifact with an owner, a changelog, tests, and a deployment path, exactly like code. Centralize prompts, version them, and run every change through the evals you built in M5.

Prompt Templates with Variable Injection

Production prompts are templates with clearly delimited slots for runtime data: user input, retrieved context, account metadata. Injection points are where prompts break, so delimit and sanitize injected content so user text cannot masquerade as instructions, and enforce length limits on every variable. A template that breaks on adversarial inputs is not production ready.

Guardrails and Output Validation

Never trust raw model output in a pipeline. Validate structure with schemas, check values against allowed ranges and enums, and confirm required fields exist before anything downstream consumes them. For a data extraction system that must never hallucinate field values: instruct the model to return null for missing data, then reject any value not traceable to the source text.

Graceful Failure Handling

Models fail: malformed JSON, refusals, truncation, timeouts. Design the failure path first. Retry with the validation error fed back to the model, fall back to a different model or simpler prompt, and when all else fails, return a safe degraded output: a template response or a human escalation. Log every failure.

Prompt Libraries and Reuse

Your extraction pattern, your brand-voice pattern, your classifier pattern: these are assets. A prompt library packages proven templates with their eval suites, docs, and known failure modes. The Faction standard: no builder solves the same prompting problem twice.

The Production Cost Model

Cost per call is input plus output tokens times their rates, multiplied by daily volume. Optimizing means finding the shortest prompt that still passes your eval suite. Sometimes a longer prompt on a cheaper model beats a short prompt on a premium model; only your cost model and evals can tell you which.

Your Toolkit

Template Engine with Delimited Injection: One templating layer that renders every prompt from versioned templates, with fenced variable slots and sanitization built in.
Schema Validator on Every Output: JSON Schema or equivalent validation as a mandatory gate between model output and downstream code, wired to trigger retries automatically on failure.
Fallback Chain Configuration: A declared ordered list per prompt: primary model, retry with error feedback, fallback model, degraded static response. Written down and tested, not improvised.
Prompt Cost Dashboard: A running tally of tokens per call, calls per day, and cache hit rate for each production prompt, so cost regressions surface as fast as quality regressions.

Common Pitfalls

Hardcoding prompts inline across the codebase: Versions drift, changes require hunting through files, and no prompt ever gets properly tested.
Trusting model output without validation: One malformed response breaks everything downstream, and hallucinated values flow silently into your data.
Retrying blindly without feedback: Resending the identical prompt usually reproduces the failure. Feed the validation error back.
Ignoring injection risk in template variables: Raw user text in a prompt slot can override your instructions. Delimit and sanitize everything you inject.
Optimizing prompt length by feel instead of by evals: Cutting tokens without rerunning evals trades invisible quality losses for visible cost savings, and the quality losses cost more.
Breaking cache with volatile prefixes: Timestamps or user IDs at the top of the prompt invalidate the cached prefix on every call and multiply input costs.
