What This Module Covers

By Module 5 you have a backend that does real work: tables, RLS policies, auth, storage, realtime, and Edge Functions. Module 6 is about protecting all of it. You will learn how Supabase handles backups, when automatic daily backups are enough and when you need point-in-time recovery, and how to take a manual pg_dump so you always hold your own copy of your data.

The second half is about environments. Right now you probably have one Supabase project and it is production. That works until the day your AI runs a migration that drops a column full of live customer data. You will set up a proper chain: local development with the Supabase CLI, a staging project that mirrors production, and production itself, plus branching, migrations, and seed data so staging behaves like the real thing.

Most importantly, you will direct your AI to follow a deployment process that never touches production directly: write a SQL migration, test it locally, apply it to staging, verify, then promote to production. Your job is to supervise that pipeline, not to hand-run SQL against live data.

Why It Matters

Think about your SaaS app with 50 tenants. A bad migration that truncates a table, a careless UPDATE without a WHERE clause, or an AI-generated script run against the wrong project can destroy months of customer records in seconds. Without backups, that data is gone and so is your business. With daily backups you lose at most a day; with point-in-time recovery, minutes. The difference is a plan you set up before the disaster, not after.

Environment separation is the other half of the same insurance policy. Builders who prototype fast tend to ship straight to production because there is nowhere else to ship. That is fine at zero users and reckless at fifty tenants. A staging project costs minutes to set up and saves you the 2 a.m. incident where a client portal shows the wrong role's data because an untested migration broke a policy.

What You Need to Know

Supabase Automatic Backups

Every paid Supabase project gets automatic daily backups, retained for a window that depends on your plan. These are full database snapshots you can restore from the dashboard. Know what they cover, the database, and what they do not, such as Storage objects, which need their own backup strategy.

Point-in-Time Recovery (PITR)

PITR, available on the Pro plan and above as an add-on, continuously archives write-ahead logs so you can restore your database to any moment in the retention window. Daily backups mean a bad migration at 4 p.m. costs the whole day's data; with PITR you roll back to 3:59 p.m. For any app with paying users, treat PITR as mandatory.

Manual pg_dump

Supabase runs on plain Postgres, so pg_dump works exactly as it does anywhere. A scheduled pg_dump gives you an off-platform copy you control, independent of your Supabase plan or account status. Direct your AI to script it, store dumps somewhere separate like S3, and test a restore at least once.

Environment Separation

A serious build runs three environments: local (the Supabase CLI running the full stack in Docker), staging (a separate Supabase project with fake data), and production (real users, real data). Each has its own project, API keys, and env vars. Your app switches between them by configuration, never by editing code.

Migrations and Branching

A migration is a versioned SQL file describing one schema change. The CLI tracks these files in your repo and applies them in order, so every environment can be rebuilt identically. Supabase branching goes further, spinning up a temporary preview database per Git branch so each pull request gets its own isolated schema.

Seeding Test Data

An empty staging database tests nothing. A seed file populates local and staging with realistic fake data: 50 fake tenants, users in multiple roles, sample uploads. Good seed data is what lets you verify the RLS policies from Module 3 actually isolate tenants before real tenants depend on it.

Your Toolkit

Supabase CLI: The command center for this module. supabase start runs the stack locally, supabase db diff and supabase migration new create migration files, supabase db push applies them to a linked remote project.
The Backups Dashboard: Where you confirm daily backups exist, enable PITR, and trigger restores. Check it now, not during an incident.
pg_dump and pg_restore: Standard Postgres tools for manual, off-platform backups. Have your AI write a scheduled script and document the restore procedure next to it.
Seed Files: A version-controlled seed.sql that loads realistic multi-tenant test data into local and staging. Rebuild it whenever your schema changes so tests stay honest.

Common Pitfalls

Treating production as your only environment. Every experiment happens on live data, so your first serious mistake is also a customer-facing incident.
Assuming backups exist without checking. Builders on the wrong plan discover at restore time that there is nothing to restore.
Letting AI run SQL directly against production. An agent with a production connection string will happily execute a destructive statement. Give it local and staging access, and gate production behind your review.
Making schema changes in the dashboard instead of migrations. Dashboard edits leave no versioned record, so environments drift apart and migrations start failing unpredictably.
Testing on empty or unrealistic seed data. A migration that works on three rows can fail on 50 tenants of real data, and empty tables never expose RLS leaks.
Ignoring Storage in your backup plan. Database restores do not bring back deleted marketplace uploads. Files need their own backup path.
