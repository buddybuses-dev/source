What This Module Covers

Module 2 is where your Supabase project stops being an empty shell and becomes a real data model. You will direct AI to design Postgres tables with the right data types, primary keys, foreign keys, and constraints, then wire them together with one-to-many and many-to-many relationships. You already completed Database Design and Migration, so the theory is not new. What is new is applying it inside Supabase, where every schema decision becomes the foundation that Row-Level Security, Auth, and Storage sit on.

You will also learn the two ways schema changes happen in Supabase, the visual table editor and SQL migrations, and when each is appropriate. Most importantly, this module teaches you to direct AI toward a data model that supports your app's real queries, not just a clean entity diagram. Your job as the builder is to hand AI the actual access patterns, then verify the schema it produces can serve them.

Why It Matters

Schema mistakes are the most expensive mistakes in your stack because everything else depends on them. Picture your SaaS app with 50 tenants. If AI builds an invoices table without a tenant_id foreign key, there is nothing for Module 3's security policies to filter on. You cannot write a policy that says "only show rows belonging to this tenant" when the column does not exist. Every table missing that link is a data leak waiting for its first curious user.

Constraints matter just as much. A marketplace where listings.seller_id is a nullable text field instead of a NOT NULL foreign key will happily accept orphaned listings and broken data. AI generates plausible schemas by default, not correct ones, and your review is the quality gate. Fixing a schema after real users have written real data means migrations under pressure and backfill scripts. Fixing it now costs one prompt.

What You Need to Know

Data Types That Match Reality

Demand precise types from your AI: uuid for identifiers, timestamptz for time, numeric for money, jsonb for flexible metadata, boolean for flags. When AI reaches for text everywhere or stores prices as floats, push back. The wrong type invites bad data and blocks the queries and indexes you will need later.

Primary Keys and Foreign Keys

Every table needs a primary key, and in Supabase the standard is a uuid default of gen_random_uuid() so keys are unguessable. Foreign keys are enforcement, not documentation: orders.customer_id references customers(id) means Postgres refuses an order pointing at a customer that does not exist. Always choose the delete behavior, on delete cascade or on delete restrict, deliberately instead of accepting AI's default.

Constraints as Your First Security Layer

NOT NULL, UNIQUE, and CHECK constraints reject bad data before it lands. A client portal's memberships table should carry unique (user_id, client_id) and a check (role in ('admin', 'member', 'viewer')) so invented roles cannot sneak in. Constraints run inside the database, so they hold even when AI-generated app code has bugs.

One-to-Many and Many-to-Many

One-to-many is a foreign key on the "many" side: one tenant has many projects, so projects.tenant_id points at tenants.id. Many-to-many requires a junction table: listings and categories connect through listing_categories (listing_id, category_id) with a composite unique constraint. When AI models a many-to-many as an array column, that is a red flag you now know how to catch.

Normalize First, Denormalize Deliberately

Normalized tables keep every fact in one place, which prevents update anomalies. Denormalize only when a real query pattern demands it: caching review_count on listings beats joining thousands of reviews on every marketplace search. Direct AI to start normalized, then denormalize specific hot paths and document why, never the reverse.

Table Editor vs SQL Migrations

The table editor is great for prototyping, but its changes live only in that one project's database. SQL migration files are versioned, reviewable, and repeatable across staging and production, which Module 6 depends on. Every schema change that matters ships as a migration file your AI writes and you review.

Your Toolkit

Supabase Table Editor: The dashboard's visual schema browser. Use it to inspect what actually exists and sanity-check AI's work, not as your system of record for schema changes.
SQL Editor and Migration Files: Run AI-generated DDL in the SQL editor, then persist it as migration files with the Supabase CLI (supabase migration new, supabase db push). This is how your schema becomes reproducible.
Schema Visualizer: Supabase's built-in relationship diagram. Pull it up after every AI schema change and verify the foreign key lines match your app's relationships. A missing line is a missing constraint.
Query-First Review Practice: Before approving any AI-generated schema, list your app's five most common queries and walk each through the tables. If a query needs a missing join path or filter column, the model fails review.

Common Pitfalls

Accepting AI's entity diagram as the data model: A diagram shows what exists, not what gets queried. A schema that cannot efficiently answer "show this tenant's unpaid invoices" fails in production no matter how clean it looks.
Missing tenant or owner foreign keys: If a table in your 50-tenant SaaS lacks tenant_id, Module 3's RLS policies have nothing to filter on. This is the most dangerous omission in a multi-tenant schema.
Text columns doing a constraint's job: Roles and statuses stored as free text with no CHECK means the database accepts anything. Six months in, you will find Admin, admin, and ADMIN in the same column.
Modeling many-to-many with array columns: Arrays skip referential integrity and break the indexing and RLS patterns you need later. If two entities relate in both directions, demand a junction table.
Clicking schema changes into production via the table editor: Untracked dashboard changes cannot be reviewed, replayed on staging, or rolled back cleanly. When environments drift, debugging becomes guesswork.
Premature denormalization: Duplicating data before any query is slow trades real integrity for imagined performance, and every duplicate copy is a future inconsistency to reconcile.
