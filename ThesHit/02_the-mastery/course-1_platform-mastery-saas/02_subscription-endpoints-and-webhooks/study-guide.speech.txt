What This Module Covers

This module covers APIs and backend logic as they apply specifically to SaaS applications—the subscription endpoints, Stripe webhook handlers, usage-tracking APIs, and billing lifecycle management that make a subscription product actually collect revenue. You already know API fundamentals from the CADE program. This goes deeper into the patterns that separate a

SaaS backend from a regular app: webhook idempotency, subscription state machines, trial-to-paid conversion flows, and the terrifying moment when a payment fails and your system needs to decide what happens next. Your AI coding tool can scaffold a Stripe integration in an hour. But if the webhook handler doesn’t verify signatures, if a failed payment doesn’t trigger a grace period, or if your subscription endpoint doesn’t handle the difference between a plan change and a cancellation—you’ll lose revenue silently and won’t know until customers complain.

Why It Matters

The subscription API is your cash register. Every bug in this layer costs you real money. A webhook handler that processes the same event twice charges a customer twice. A cancellation endpoint that doesn’t actually cancel the Stripe subscription means you’re billing people who left. A trial expiration flow that doesn’t prompt conversion means you’re giving away your product for free indefinitely. Stripe’s API is well-documented and AI tools generate clean Stripe integrations. But the hard part isn’t calling the Stripe API—it’s handling every edge case in the subscription lifecycle. What happens when a card expires? What happens when a customer disputes a charge? What happens when they upgrade mid-cycle? These decisions determine whether your SaaS makes money or leaks it.

Module Certification Goal

You can describe subscription API endpoints and Stripe webhook handlers to an AI coding tool, evaluate the output for idempotency, signature verification, and proper lifecycle management, and ship a billing backend that collects revenue without losing money to duplicate charges, missed cancellations, or unhandled payment failures.

What You Need to Know

Stripe webhook fundamentals: When something happens in Stripe—a payment succeeds, a subscription renews, a card expires—Stripe sends an HTTP POST to a URL you configure. Your app needs to listen for these events, verify they came from Stripe (signature verification), and process them correctly. If your endpoint is down, Stripe retries—but your app needs to handle receiving the same event more than once without processing it twice.

Idempotency in billing: Idempotency means processing the same request multiple times produces the same result as processing it once. If Stripe sends a payment_succeeded webhook twice, your system should not credit the account twice or send two confirmation emails. You do this by tracking which events you’ve already processed.

Subscription lifecycle states: A SaaS subscription moves through states: trial → active → past_due → canceled → expired. Your backend needs to handle each transition. When a trial ends, prompt for payment. When a payment fails, enter a grace period. When canceled, decide whether access ends immediately or at the billing period end. Your AI tool won’t build this state machine unless you describe every transition.

Usage-based billing APIs: Some SaaS products charge based on usage—API calls, storage, active users. Your backend needs endpoints that track usage, enforce limits, and report to Stripe for metered billing. This means your API needs to count things accurately, in real time, and handle what happens when a customer hits their limit.

Plan change logic: Upgrading and downgrading are different operations. An upgrade usually takes effect immediately with a prorated charge. A downgrade usually takes effect at the end of the billing period. Your API needs to handle both cases and communicate with Stripe accordingly.

Webhook signature verification: Every incoming webhook should be verified using Stripe’s webhook signing secret. This confirms the request came from Stripe and wasn’t spoofed. Without this check, anyone who discovers your webhook URL could send fake payment confirmations.

Certification Exam Topics

Every exam question is scenario-based. You’ll see a situation and need to identify what’s right, what’s wrong, or what to do next. Here’s what gets tested:

Webhook handling: Can you evaluate whether a webhook handler verifies Stripe signatures, handles duplicate events, and responds with the correct status codes?

Idempotency: Can you identify when a billing operation would produce duplicate charges or repeated emails if the same event is processed twice?

Subscription state management: Can you trace a subscription through its lifecycle—trial to active to past_due to canceled—and verify each transition is handled correctly?

Payment failure handling: Can you evaluate what happens when a payment fails—grace period, retry logic, customer notification, and eventual access revocation?

Plan change logic: Can you assess whether an upgrade takes effect immediately with proration and a downgrade takes effect at period end?

Usage tracking: Can you verify that usage-based billing endpoints count accurately, enforce limits, and handle what happens when a customer exceeds their allocation?

Security: Can you spot when a webhook endpoint is missing signature verification or when API keys are exposed in client-side code?

Error responses: Can you evaluate whether billing APIs return clear, actionable error messages when a payment fails or a webhook can’t be processed?

Common Pitfalls

These are the mistakes vibecoders make most often in this area. No judgment—they’re easy to make. But if you recognize any of them in your own workflow, fix them before sitting for the exam. Not verifying Stripe webhook signatures. Without verification, anyone who discovers your webhook URL can send fake payment events and your system will process them as real. Processing the same webhook event multiple times. Stripe retries failed deliveries, so your handler might receive the same event 3-5 times. Without tracking processed events, you’ll charge customers multiple times or send duplicate emails. Building a cancellation endpoint that removes access immediately instead of at the end of the paid billing period. The customer paid for the full month—cutting them off early is wrong and will generate disputes. Not handling the past_due state. When a payment fails, your system should enter a grace period where the customer can update their card. Cutting off access on the first failed charge is aggressive and loses recoverable revenue. Storing Stripe API keys in your frontend code. Secret keys belong in environment variables on your server. If your secret key is in the frontend, anyone can view your source and access your Stripe account. Hardcoding plan IDs in your codebase. When you create new plans in Stripe, you’ll have to redeploy just to reference them. Use a config or database instead.

Self-Assessment Checklist

Before you take the exam, run through these questions. Every “no” is something to work on. Can you describe a Stripe webhook handler to AI that includes signature verification, idempotency checks, and proper HTTP response codes? Does your webhook handler track which events it has already processed to prevent duplicate charges? Does your system handle the full subscription lifecycle—trial end, payment success, payment failure, plan change, and cancellation? When a payment fails, does your system enter a grace period and notify the customer, or does it immediately revoke access? Are your Stripe API keys stored in environment variables on the server—not in frontend code or committed to your repository? Can you test webhooks locally using the Stripe CLI before deploying to production? Does your cancellation flow end access at the end of the billing period, not immediately?
